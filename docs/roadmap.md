## ۱. خواندن کسب‌وکار

**محصولی که امروز ساخته شده:** یک اپ اندروید فارسی که دستور صوتی/متنی را به نیت تبدیل می‌کند،
روی Supabase اجرا می‌کند، روی GitHub آینه می‌کند، و یک تیم ایجنت رایگان روی GitHub Actions
کد را واقعاً می‌نویسد و merge می‌کند.

**محصولی که واقعاً دارید:** یک **کارخانهٔ نرم‌افزارِ فارسی‌زبان برای غیربرنامه‌نویس‌ها**.
ارزش اصلی «مدیریت وظیفه» نیست — مدیریت وظیفه ده‌ها رقیب دارد. ارزش اصلی این جمله است:

> «فارسی حرف بزن، فردا کدش روی مخزن merge شده است.»

سه دارایی که این ادعا را از یک دموی معمولی جدا می‌کند و در بازار کمیاب‌اند:

| دارایی | چرا کمیاب است |
|---|---|
| **ورودی فارسیِ صوتی با نرمال‌سازی و بازنویسی پرامپت** | مسیر سه‌مرحله‌ای (نرمال‌سازی روی دستگاه → بازنویسی → استخراج JSON) دقیقاً همان چیزی است که رقبای انگلیسی‌زبان لازم ندارند و برای فارسی کسی نساخته. |
| **هزینهٔ صفر و شفاف** | کل خط تولید روی مدل‌های رایگان می‌چرخد و **هر ریال/توکن روی همان ایشو ثبت می‌شود**. این «حساب‌وکتاب روی ایشو» یک تمایز واقعی است، نه یک فیچر جانبی. |
| **تیم نقش‌محور (PO/TEC/QC)** | زیرساخت چندایجنتی روی GitHub Actions بدون هیچ سرور اختصاصی — تکثیرش برای هر مخزن جدید فقط شش فایل است. |

**مشتری هدف (به ترتیب واقع‌بینی):**

1. **بنیان‌گذار تک‌نفره / فریلنسر فارسی‌زبان** — ایده دارد، وقتِ کدزدنِ کارهای تکراری ندارد.
2. **تیم‌های کوچک ۲–۵ نفره** — می‌خواهند کارهای درجه‌۳ (CRUD، فرم، ترجمه، تغییر UI) را به ایجنت بدهند.
3. **مدرس/دانشجو** — می‌خواهد ببیند یک تیم ایجنتی واقعی چطور کار می‌کند.

**درآمدِ ممکن (برای وقتی که لازم شد):** اشتراک ماهانه روی «تعداد ایشوی موفقِ merge‌شده»
نه روی توکن — چون واحدِ ارزشِ کاربر یک تغییرِ کارکردی است، نه یک فراخوانی مدل.

## ۲. زنجیرهٔ ارزش امروز و شش نقطهٔ شکست

<div dir="ltr">

```
 گفتار/متن فارسی → نیت JSON → Supabase → Issue → TEC → PR → merge → ???
      ①              ②           ③        ④      ⑤     ⑥
```

</div>

| # | نقطهٔ شکست | چه اتفاقی می‌افتد | اثر روی کسب‌وکار |
|---|---|---|---|
| ① | **واژگان نیت خیلی کوچک است** | فقط چهار کنش: `create_project`، `delete_project`، `add_task`، `remove_task`. کاربر نمی‌تواند بگوید «این تسک را ببند»، «اولویتش را بالا ببر»، «به فلانی بسپار». ستون `is_done` در دیتابیس هست، در `ProjectCard` هم نمایش داده می‌شود، اما **هیچ مسیری آن را `true` نمی‌کند**. | کاربر بعد از دو روز به اپ برنمی‌گردد چون نمی‌تواند کار را «تمام» کند. |
| ② | **هر دستور = یک ایشوی خام** | متن کاربر تقریباً بدون پردازش به بدنهٔ ایشو می‌رود. یک جملهٔ مبهم → یک ایشوی مبهم → یک PR بی‌ربط. | نرخ موفقیت ایجنت پایین می‌ماند و کاربر ایجنت را «احمق» می‌بیند، در حالی که مشکل **کیفیت بریف** است. |
| ③ | **بدون تجزیه (decomposition)** | «یک فروشگاه اینترنتی بساز» و «یک دکمهٔ خروج اضافه کن» هر دو یک ایشو می‌شوند. مدل ضعیف روی ایشوی بزرگ همیشه شکست می‌خورد. | بزرگ‌ترین علتِ خروجی بی‌کیفیت. |
| ④ | **PO و QC منفعل‌اند** | فقط با منشن `@po`/`@qc` جواب می‌دهند و خروجی‌شان فقط یک کامنت است که هیچ‌چیز را در خط تولید تغییر نمی‌دهد. | سه نقش دارید ولی عملاً یک نقش کار می‌کند. |
| ⑤ | **یک‌شات، بدون ترمیم** | build شکست بخورد، جاب قرمز می‌شود و کار همان‌جا می‌ماند تا انسان دوباره `@tec` بزند. مدل هرگز خطای کامپایلر خودش را نمی‌بیند. | تک‌بزرگ‌ترین اهرمِ ازدست‌رفتهٔ کیفیت. |
| ⑥ | **حلقه بسته نمی‌شود** | بعد از merge هیچ‌چیز به کاربر برنمی‌گردد: نه اعلان، نه APK، نه اسکرین‌شات، نه بسته‌شدن تسک در Supabase. | کاربر نمی‌داند کارش انجام شده؛ «جادو» دیده نمی‌شود. |

سه گلوگاه دیگر که فیچر نیستند ولی رشد را می‌بندند: **تک‌کاربره بودن** (بدون تیم/نقش انسانی)،
**تم روشنِ ناقص** (`MIALightColorScheme` فقط دو رنگ را override می‌کند در حالی که کل اپ dark-first است)،
و **نبود تأیید برای کنش‌های مخرب** (یک «حذف پروژه»ی بدشنیده‌شده، پروژه و همهٔ تسک‌هایش را با
`on delete cascade` می‌برد).

## ۳. فیچر اصلی: سند نیت → اپیک → ایشوهای کوچک

این همان چیزی است که خواسته‌اید: **دستیار نیت را می‌نویسد، ایجنت آن را به ایشو تبدیل می‌کند،
و هر ایشو را یک ایجنت پیاده می‌کند.** امروز مرحلهٔ وسط (تجزیه) وجود ندارد.

<div dir="ltr">

```
 کاربر (صوتی/متنی/چندپاراگرافی)
        │  "یک بخش پروفایل کاربر می‌خوام با آواتار و ویرایش نام و خروج از حساب"
        ▼
 ┌─ BRIEF (سند نیت) ──────────────────────────────────────────────┐
 │  در اپ: صفحهٔ «نیت جدید» — عنوان، شرح، مخاطب، معیار موفقیت      │
 │  خروجی: یک Issue با برچسب `brief` (نه `by-agent`)              │
 └───────────────────────────┬────────────────────────────────────┘
                             ▼
 ┌─ PO AGENT (تجزیه‌گر) ────────────────────────────────────────────┐
 │  ۱. brief را می‌خواند + repo map را می‌خواند                     │
 │  ۲. خروجی JSON: { epic, issues[ {title, spec, files[], deps[],  │
 │       size: S|M|L, acceptance[] } ] }                            │
 │  ۳. برای هر آیتم یک Issue باز می‌کند با قالب ماشین‌خوان          │
 │  ۴. ترتیب وابستگی را با `blocked-by: #n` می‌نویسد               │
 │  ۵. فقط ایشوهای size=S که وابستگیِ باز ندارند → `agent-ready`   │
 └───────────────────────────┬────────────────────────────────────┘
                             ▼
 ┌─ TEC (پیاده‌ساز) ─ روی `agent-ready`، نه روی `by-agent` خام ────┐
 │  PLAN → APPLY → VERIFY → REPAIR (بخش ۵)                         │
 └───────────────────────────┬────────────────────────────────────┘
                             ▼
 ┌─ QC (دروازه‌بان PR) ────────────────────────────────────────────┐
 │  diff را در برابر acceptance criteria بررسی می‌کند              │
 │  پاس → merge · رد → `needs-rework` → TEC دوباره (حداکثر ۲ بار)  │
 └───────────────────────────┬────────────────────────────────────┘
                             ▼
        merge → بسته‌شدن ایشو → آزادشدن ایشوهای `blocked-by` بعدی
                → به‌روزرسانی `is_done` در Supabase → اعلان روی گوشی
```

</div>

**چرا این تک‌فیچر بیشترین اثر را دارد:** یک مدل ضعیف روی «یک تغییر کوچک با معیار پذیرش صریح»
تقریباً همیشه موفق است و روی «یک خواستهٔ بزرگ و مبهم» تقریباً همیشه شکست می‌خورد.
تجزیه، کارِ سختِ فکری را به یک مدلِ **متنی** (که رایگان و خوب است) می‌سپارد و کارِ **کدنویسی**
را آن‌قدر کوچک می‌کند که از عهدهٔ مدل ضعیف بربیاید.

**قالب ماشین‌خوانِ ایشو** (خروجی PO؛ همین قالب ورودی TEC و چک‌لیست QC است):

<div dir="ltr">

```markdown
## Goal
One sentence. What the user can do after this change that they cannot do today.

## Context
Repo: android/kotlin/compose · Module: `app` · Related: #12, #14

## Files to touch  (TEC may not modify anything outside this list)
- app/src/main/java/.../ui/profile/ProfileScreen.kt   (new)
- app/src/main/java/.../ui/MiaApp.kt                  (add route)

## Acceptance criteria  (each must be objectively checkable)
- [ ] AC1: `ProfileScreen` composable exists and renders the user's name
- [ ] AC2: tapping "خروج" calls `AuthViewModel.logout()`
- [ ] AC3: `./gradlew assembleDebug testDebugUnitTest` passes
- [ ] AC4: no raw `Color(0x...)` or hard-coded `dp` — use `MiaTheme` tokens only

## Out of scope
Avatar upload, server-side profile storage.

## Test plan
Unit: `ProfileScreenTest` asserts AC1/AC2 via Compose test rule.

## Size
S   (S ≤ 2 files · M ≤ 5 files · L → must be split, never given to TEC)
```

</div>

> **قانون طلایی:** هر ایشویی که `Size: L` بخورد **هرگز** به TEC نمی‌رسد؛ به PO برمی‌گردد
> تا دوباره تجزیه شود. این یک خط شرط در ورک‌فلو است و بیشترین بازده را در کل سیستم دارد.

## ۵. پروتکل «مدل ضعیف، خروجی قوی»

مدل رایگان ضعیف نیست چون کم‌هوش است؛ ضعیف است چون **کانتکست کم، پایداری کم و توانِ برنامه‌ریزی
بلند کمی دارد**. هر ده اهرم زیر دقیقاً همین سه ضعف را جبران می‌کنند و هیچ‌کدام به مدل بهتر نیاز ندارند.

### ۵.۱. کوچک‌سازی اجباری کار
یک ایجنتِ ضعیف روی تغییرِ «۲ فایل / ۸۰ خط» قابل‌اتکاست و روی «۹ فایل» نیست.
`Size: S|M|L` را در ایشو اجباری کنید و در ورک‌فلو شرط بگذارید: `L` → TEC اجرا نشود.

### ۵.۲. حافظهٔ مخزن: `AGENTS.md`
مهم‌ترین فایلی که ندارید. در ریشهٔ هر مخزن، تولیدشده و به‌روزشونده:

<div dir="ltr">

```markdown
# AGENTS.md — read this before editing anything

## Stack
Kotlin 2.x · Jetpack Compose (Material 3) · Retrofit + kotlinx.serialization · no DI framework

## Commands
build:  ./gradlew assembleDebug
test:   ./gradlew testDebugUnitTest
format: ./gradlew ktlintFormat      # ALWAYS run before finishing

## Where things live
ui/<feature>/   Screen.kt + ViewModel.kt + UiState.kt   (one folder per feature)
data/repository/  business logic, suspend functions, never touches Compose
network/<service>/  Retrofit interface + @Serializable models
network/NetworkModule.kt  manual DI — every new API client is wired HERE

## Hard rules (a PR violating any of these is rejected)
1. RTL: the app is Persian-first. Never hard-code LayoutDirection.
2. Colors/spacing come from ui/theme only. Never write Color(0x..) or a raw dp in a screen.
3. Every new screen gets a ViewModel exposing StateFlow<UiState>. No state in composables.
4. All user-facing strings go in res/values/strings.xml (fa). No literals in code.
5. Never add a dependency without saying why in the PR body.

## How to add a new screen (follow this exactly)
1. create ui/<feature>/<Name>Screen.kt using MiaScaffold + MiaCard from ui/design
2. create ui/<feature>/<Name>ViewModel.kt extending AndroidViewModel
3. register the route in ui/MiaApp.kt
4. add a unit test in src/test/.../<Name>ViewModelTest.kt
```

</div>

این فایل را به‌عنوان asset هفتم به `RepoBootstrapper` اضافه کنید و در پرامپت TEC **قبل از**
متن ایشو تزریق کنید. تنها همین کار، یکدستیِ خروجیِ مدل ضعیف را به شکل محسوسی بالا می‌برد.

### ۵.۳. دو فاز: PLAN سپس APPLY
یک بار مدل را **بدون ابزار** صدا بزنید و فقط یک نقشهٔ JSON بگیرید، آن را روی ایشو کامنت کنید،
بعد در فراخوانی دوم همان نقشه را به‌عنوان دستور به OpenCode بدهید:

<div dir="ltr">

```json
{ "understanding": "...", "files": [
    { "path": "app/src/.../ProfileScreen.kt", "action": "create",
      "what": "Compose screen showing name + logout button" } ],
  "risks": ["MiaApp.kt route table must be updated"] }
```

</div>

نقشه هم دقت را بالا می‌برد (مدل قبل از ویرایش «فکر» می‌کند) و هم به انسان یک نقطهٔ توقف ارزان می‌دهد.

### ۵.۴. محدود کردن سطح تماس (path allowlist)
بعد از اجرای ایجنت و قبل از commit:

<div dir="ltr">

```bash
# ALLOWED comes from the issue's "Files to touch" block
git diff --name-only | while read -r f; do
  grep -qxF "$f" "$ALLOWED" || { echo "::error::agent touched out-of-scope file: $f"; exit 1; }
done
```

</div>

مدل ضعیف عادت دارد فایل‌های نامربوط را «مرتب» کند؛ این چهار خط جلوی diffهای غول‌آسا را می‌گیرد.

### ۵.۵. حلقهٔ ترمیم (مهم‌ترین اهرم)
امروز `assembleDebug` که بشکند، جاب قرمز می‌شود و تمام. به‌جایش:

<div dir="ltr">

```bash
for attempt in 1 2 3; do
  if ./gradlew ktlintFormat assembleDebug testDebugUnitTest 2>&1 | tee "$log"; then
    echo "green after $attempt attempt(s)"; break
  fi
  [ "$attempt" = 3 ] && { echo "status=unfixable" >> "$GITHUB_OUTPUT"; break; }
  # feed the model ONLY the compiler errors, not the whole log
  tail -c 6000 "$log" | grep -E "^e:|error:|FAILED|expected" > "$RUNNER_TEMP/errors.txt"
  opencode run $approve -m "$AGENT_MODEL" "$(cat <<PROMPT
Your previous change does not compile. Fix ONLY these errors. Do not add features.
$(cat "$RUNNER_TEMP/errors.txt")
PROMPT
)"
done
```

</div>

هیچ چیز دیگری به اندازهٔ «دادن پیام خطای کامپایلر به همان مدل» نرخ موفقیت را بالا نمی‌برد،
چون خطای کامپایلر یک **سیگنالِ دقیق و ماشینی** است — دقیقاً چیزی که مدل ضعیف در تولید آن ناتوان
است ولی در مصرف آن خوب.

### ۵.۶. تست به‌عنوان قرارداد (TDD معکوس)
QC قبل از TEC یک تست **شکست‌خورده** از روی acceptance criteria می‌نویسد و روی شاخه commit می‌کند.
TEC فقط باید آن را سبز کند. هدف از «متن مبهم» به «یک تست مشخص» تبدیل می‌شود —
و این تفاوت بین ۳۰٪ و ۷۰٪ موفقیت است.

### ۵.۷. تولید قالبی به‌جای تولید آزاد
برای کلاس‌های تکراری (صفحهٔ جدید، فیلد جدید، اندپوینت جدید) قالب بگذارید در
`.github/agent/templates/` و بگذارید PO ایشو را به یک «recipe» نگاشت کند.
مدل فقط بدنه را پر می‌کند، اسکلت را ننویسد. کیفیت اسکلت آن‌وقت **مستقل از مدل** است.

### ۵.۸. نردبان مدل و بودجه

<div dir="ltr">

```yaml
AGENT_MODEL_LADDER: >-
  openrouter/minimax/minimax-m3:free,
  openrouter/cohere/north-mini-code:free,
  openrouter/z-ai/glm-5.2:free
```

</div>

شکست (نه ۴۲۹، بلکه شکستِ کیفی: build سبز نشد) → پلهٔ بعدی. هر پله روی همان ایشو گزارش می‌شود
تا هزینه/کیفیت هر مدل به‌مرور داده شود، نه حدس. با تجمیع همین داده در «صفحهٔ هزینه» می‌فهمید
کدام مدل رایگان واقعاً ارزش دارد.

### ۵.۹. کانتکست کم اما پرسیگنال
کل مخزن را به مدل ندهید (و با ۱M کانتکست هم ندهید — نویز، دقت را پایین می‌آورد). بدهید:
`AGENTS.md` + خروجی `git ls-files` + **فقط** فایل‌های `Files to touch` + فایل‌هایی که با
کلیدواژه‌های spec در `grep` پیدا می‌شوند.

### ۵.۱۰. تخریب تمیز، همیشه
اصلِ درستی که در ورک‌فلوی امروز رعایت شده را حفظ کنید: نبود کلید، سقف نرخ، نبود اجازهٔ PR —
هیچ‌کدام نباید کرش باشند؛ باید یک کامنت راهنما باشند. هر مسیر شکست جدیدی هم که اضافه می‌کنید
باید همین قاعده را داشته باشد.

## ۶. نقش‌ها: PO / TEC / QC به‌عنوان یک خط تولید

> **وضعیت: ✅ پیاده شد** (و از این هم فراتر رفت) — ← [مستندات تیم](github/README.md#۴۹-قرارداد-تحویل-و-حالتها)
> و [پرامپت‌های موج ۵](agent-humanity-prompts.md). هر سه نقش دروازه شدند، و روی آن دو چیز اضافه
> شد که این جدول پیش‌بینی‌شان نکرده بود: **امضای تحویل** (هیچ پیامی بدون نامِ نفر بعد پست
> نمی‌شود؛ در کد اجباری است) و **چوپان** (هر نیم‌ساعت دنبال کاری می‌گردد که کسی رویش کار نمی‌کند).
> جدول زیر طرح اولیه است و برای مقایسه نگه داشته شده.

| نقش | محرک (رویداد) | ورودی | خروجی ماشین‌خوان | برچسبی که می‌گذارد |
|---|---|---|---|---|
| **PO** | ایشوی `brief` باز شد | brief + repo map | اپیک + N ایشوی S/M با acceptance criteria | `agent-ready` روی آماده‌ها، `blocked` روی بقیه |
| **QC (پیش)** | ایشو `agent-ready` شد | acceptance criteria | یک تستِ شکست‌خورده روی شاخهٔ ایشو | `has-test` |
| **TEC** | ایشو `has-test` شد | AGENTS.md + spec + فایل‌های مجاز | diff محدود به allowlist + PR | `in-review` |
| **QC (پس)** | PR باز شد | diff + acceptance criteria | ✅/❌ برای هر AC | `approved` یا `needs-rework` |
| **TEC (ترمیم)** | `needs-rework` | نظر QC + خطاها | diff اصلاحی (حداکثر ۲ دور) | `in-review` یا `needs-human` |

قواعدی که این خط تولید را از قفل‌شدن نجات می‌دهد:

- **سقف چرخه:** حداکثر ۲ دور rework، بعد `needs-human`. بدون این، دو ایجنت می‌توانند تا سوختن
  کل سهمیهٔ روزانه با هم بحث کنند.
  <br>**آنچه واقعاً ساخته شد فرق دارد:** دو دور rework بعد به **PO** می‌رود نه به `needs-human`،
  و `needs-human` وقتی هم برسد یک **مکثِ صاحب‌دار** است: پرسش، پاسخِ پیش‌فرض، مهلت، و بازگشت
  خودکار با هر کامنت. سقف، جای «تسلیم شو»، معنای «از یک آدم بپرس» را گرفت — چون کاری که دیگر
  رویش کار نمی‌شود، همان شکستی است که کل این خط تولید برای جلوگیری از آن ساخته شده.
- **جلوگیری از حلقه:** شرط `comment.user.type != 'Bot'` امروز درست است؛ برای مسیرِ برچسب‌محورِ
  جدید هم به یک شرط معادل نیاز دارید (مثلاً برچسب‌گذارِ ربات را با `github.actor` فیلتر کنید).
- **همه‌چیز روی ایشو ثبت شود:** ایشو باید دفتر کلِ آن تسک باشد — spec، نقشه، خطاها، مصرف،
  نتیجهٔ QC. این همان ایده‌ای است که امروز برای توکن‌ها دارید؛ فقط تعمیمش بدهید.
  <br>**پیاده شد** به‌شکل `ledger.js`: یک کامنت زنده روی هر ایشو («وضعیت | مالک فعلی | قدم بعدی |
  دور بازکاری | بازتعریف PO | تلاش TEC | شاخه/PR | آخرین حرکت») که در جا به‌روز می‌شود. عمداً
  **مشتق** است: هرچه در آن هست از روی خودِ رشتهٔ کامنت‌ها قابل بازسازی است، پس دفترِ گم‌شده به
  خواننده کمی اسکرول تحمیل می‌کند و به ماشین هیچ.

## ۷. UI/UX — اپ MIA

اپ امروز یک ستون فقرات درست دارد (Compose، RTL سراسری، تم نئونیِ تیره، Vazirmatn، سه حالت ضبط).
چیزی که کم دارد **بازخورد** است: کاربر بعد از «ارسال» تا مدت‌ها نمی‌داند چه شد.

### ۷.۱. تایم‌لاین زنده — مهم‌ترین تغییر UI
امروز `StatusBanner` سه حالت متنی نشان می‌دهد و بعد از ساخته‌شدن ایشو ساکت می‌شود.
به‌جایش یک **stepper عمودی** که تا آخر خط تولید ادامه دارد:

<div dir="ltr">

```
 ● دستور دریافت شد                                   ۰۰:۰۰
 ● پرامپت بازنویسی شد                     ۱٬۲۰۰ توکن  ۰۰:۰۳
 ● نیت استخراج شد   ۲ کار شناسایی شد        ۹۰۰ توکن  ۰۰:۰۵
 ● ایشو #۱۴ باز شد                                    ۰۰:۰۶
 ◐ PO در حال تجزیه…                                   ۰۰:۱۲
 ○ TEC
 ○ بازبینی QC
 ○ merge
```

</div>

هر مرحله: آیکن وضعیت، زمان، هزینه، و لمس‌شدن → مقصدش (ایشو، run، PR). این تنها راهی است که
«جادوی» محصول برای کاربر **دیده** شود. داده‌اش هم آماده است: `GET /repos/{o}/{r}/actions/runs`
و کامنت‌های ایشو.

### ۷.۲. تأیید نیت پیش از اجرا
بعد از استخراج نیت و **پیش از** نوشتن در Supabase، یک BottomSheet:

- هر نیت یک ردیف با آیکن کنش، نام پروژه، عنوان تسک و تاریخ — همه **قابل ویرایش درجا**.
- کنش‌های مخرب (`delete_project`) با رنگ خطا و یک تأیید جداگانه (کشیدن، نه لمس).
- دکمهٔ «انجام بده» + «اصلاح می‌کنم» (متن به فیلد برمی‌گردد).

این هم ریسک را می‌بندد و هم اعتماد می‌سازد: کاربر می‌بیند که سیستم **درست فهمیده**.

### ۷.۳. کارت پروژه به‌عنوان یک داشبورد کوچک
امروز: نام، تسک‌ها، دکمهٔ 🤖، نوار «۳ باز / ۲ بسته». اضافه کنید:

- **نوار پیشرفت** بستهٔ کل تسک‌ها (وقتی `complete_task` آمد معنا پیدا می‌کند).
- **چیپ وضعیت ایجنت**: «TEC در حال کار روی #۱۴» با نبضِ ملایم، یا «۲ PR منتظر بازبینی».
- **هزینهٔ این هفته** به تومان/دلار.
- **لمس طولانی** → منوی سریع (تغییر مدل، باز کردن مخزن، آرشیو).

### ۷.۴. جزئیاتی که «حرفه‌ای بودن» را می‌سازند

| مورد | امروز | پیشنهاد |
|---|---|---|
| **تم روشن** | فقط دو رنگ override شده | یا یک تم روشنِ کامل و طراحی‌شده بسازید، یا صادقانه اپ را dark-only کنید (`Theme.kt` امروز عملاً همین است ولی وانمود می‌کند نیست) |
| **حالت خالی** | لیست خالی | تصویر + یک دستور نمونهٔ قابل‌لمس: «بگو: یک پروژه به اسم فروشگاه بساز» |
| **بارگذاری** | چرخنده | Skeleton برای کارت‌ها (چرخنده حس کندی می‌دهد) |
| **خطا** | Snackbar | خطای درون‌کارتی با دکمهٔ «تلاش دوباره» (این الگو در `ProjectCard` هست — تعمیمش بدهید) |
| **میکروفون** | نبض بر اساس RMS | نوار موج واقعی (چند میله بر اساس دامنه) + لرزش کوتاه در شروع/پایان |
| **اعداد** | `Locale.US` (درست) | فونت `tabular` برای شمارنده‌ها تا عدد نلرزد |
| **متن ایشو** | plain text | رندر Markdown محدود و امن: عنوان، لیست، **بولد**، `کد`، جدول، لینک |
| **دسترس‌پذیری** | ناقص | `contentDescription` برای همهٔ آیکن‌ها، پشتیبانی از فونت بزرگ، حداقل ۴۸dp برای هدف لمسی |
| **کلیدها** | دیالوگ تنظیمات | ویزارد راه‌اندازی سه‌مرحله‌ای با دکمهٔ «تست اتصال» برای هر کلید |
| **اعلان** | ندارد | اعلان محلی وقتی PR merge شد، با اکشن «دیدن تغییر» |

### ۷.۵. صفحهٔ هزینه
داده‌اش امروز روی ایشوها پراکنده است؛ فقط باید جمع شود: نمودار میله‌ای مصرف هفتگی،
تفکیک به تفکیک مدل و نقش، «گران‌ترین ایشو»، و یک سقف بودجه که وقتی رد شد اپ هشدار می‌دهد.
این صفحه تمایزِ «حساب‌وکتاب شفاف» را از یک جزئیات فنی به یک فیچرِ دیدنی تبدیل می‌کند.

## ۸. UI/UX — کدی که ایجنت تولید می‌کند

سؤال «چطور با مدل ضعیف UI زیبا بگیریم؟» یک جواب دارد: **نگذارید مدل UI را طراحی کند.**
مدل باید فقط قطعاتِ از پیش طراحی‌شده را کنار هم بچیند.

### ۸.۱. یک ماژول Design System در هر مخزن
هنگام bootstrap، یک `ui/design/` آماده در مخزن قرار دهید:

<div dir="ltr">

```
ui/design/
├── Tokens.kt      Spacing(4/8/12/16/24/32) · Radius · Elevation · Motion durations
├── MiaTheme.kt    color scheme + typography (Vazirmatn) + RTL default
├── MiaScaffold.kt standard screen frame: top bar + content + snackbar
├── MiaCard.kt     the only card in the app
├── MiaButton.kt   Primary / Secondary / Danger — no other button exists
├── MiaTextField.kt
├── MiaEmptyState.kt · MiaError.kt · MiaSkeleton.kt
└── README.md      "how to build a screen with these" + a full example screen
```

</div>

و در `AGENTS.md` قانون سخت: **هیچ صفحه‌ای اجازهٔ استفادهٔ مستقیم از `Color`، `dp` خام،
یا کامپوننت خام Material را ندارد.** یک تست lint ساده هم این را ماشینی چک می‌کند:

<div dir="ltr">

```bash
# fails the build if a screen hard-codes design decisions
! grep -rEn 'Color\(0x|\b[0-9]+\.dp' app/src/main/java --include='*Screen.kt' \
  || { echo "::error::use design tokens from ui/design, not raw values"; exit 1; }
```

</div>

نتیجه: خروجیِ مدل ضعیف هم **یکدست و تمیز** است، چون تنوعِ ممکن را حذف کرده‌اید.
زیباییِ UI از کیفیت مدل به کیفیت کتابخانه منتقل می‌شود — و کتابخانه را یک بار انسان می‌سازد.

### ۸.۲. صفحهٔ نمونه به‌عنوان مرجع
یک `ExampleScreen.kt` کاملِ کامنت‌گذاری‌شده در `ui/design/` بگذارید و در پرامپت بنویسید
«ساختار این فایل را کپی کن». تقلید از یک نمونهٔ خوب، کاری است که مدل‌های ضعیف در آن
**بسیار** بهترند تا طراحی از صفر.

### ۸.۳. تأییدِ چشمی خودکار
در CI با `reactivecircus/android-emulator-runner` اپ را بالا بیاورید، از صفحهٔ تغییرکرده
اسکرین‌شات بگیرید و روی PR/ایشو آپلود کنید. کاربر به‌جای خواندن diff، **تصویر** می‌بیند —
و همان تصویر بازخوردِ بعدی‌اش را می‌سازد. تست‌های اسکرین‌شات (Roborazzi/Paparazzi) هم
جلوی پس‌رفتِ ظاهری را می‌گیرند بدون اینکه به مدل اعتماد کنیم.

### ۸.۴. قوانین UX که در `AGENTS.md` باید صریح باشند
هر صفحهٔ تولیدشده باید چهار حالت داشته باشد: **loading / empty / error / content**؛
هر کنش مخرب یک تأیید؛ هر عملیات شبکه یک حالت خطا با «تلاش دوباره»؛ همهٔ متن‌ها فارسی و در
`strings.xml`. اینها را به‌صورت acceptance criteria در قالب ایشو بگذارید تا QC ماشینی چکشان کند.

## ۹. معیارهای موفقیت

بدون این اعداد، «بهتر شد» یک احساس است. هر پنج عدد را می‌شود از خودِ GitHub استخراج کرد:

| معیار | تعریف | هدف |
|---|---|---|
| **نرخ موفقیت ایجنت** | ایشوهای `agent-ready` که بدون دخالت انسان merge شدند ÷ کل | از پایه → **۷۰٪** |
| **پاس‌شدن در تلاش اول** | buildهای سبز در اولین تلاش (بدون حلقهٔ ترمیم) | > ۵۰٪ |
| **هزینه به ازای PR merge‌شده** | جمع `Token-Spend` ÷ PRهای merge‌شده | نزولی |
| **زمان از دستور تا merge** | زمان ایجاد ایشو تا merge | < ۱۵ دقیقه برای `Size: S` |
| **نرخ بازکاری** | ایشوهایی که `needs-rework` خوردند | < ۳۰٪ |

پیشنهاد: یک ورک‌فلوی هفتگی که این پنج عدد را در یک ایشوی «گزارش هفته» می‌نویسد —
با همان مدل رایگان، چون کارِ متنی است.

## ۱۰. ریسک‌ها و بدهی‌های فنی امروز

| ریسک | شرح | کاهش |
|---|---|---|
| **تزریق پرامپت از راه ایشو** | بدنهٔ ایشو ورودی نامعتمد است و مستقیم وارد پرامپتِ ایجنتی می‌شود که اجازهٔ نوشتن روی مخزن دارد. امروز فقط در برابر تزریق **شل** محافظت شده (متغیر محیطی)، نه در برابر تزریق **مدل**. | متن ایشو را در یک بلوک با مرزبندی صریح بگذارید («این داده است، نه دستور»)، اسکوپ توکن را حداقلی کنید، و گاردِ مسیر فایل (۵.۴) را اضافه کنید. |
| **حذف آبشاری** | `on delete cascade` + یک نیتِ `delete_project` بدشنیده = از دست رفتن همهٔ تسک‌ها. | تأیید اجباری (۷.۲) + حذف نرم (`deleted_at`) به‌جای حذف واقعی. |
| **کلید در APK** | هر مقدار در `BuildConfig` در APK متن ساده است — خودِ مستندات هم هشدار داده. | توکن fine-grained با حداقل دسترسی؛ در بلندمدت، انتقال عملیات GitHub به `web/server` که کلید را نگه دارد (این سرور از قبل دقیقاً برای همین ساخته شده). |
| **وابستگی به مدل‌های رایگانِ ناپایدار** | `stealth/ox-alpha` یک بار حذف شد و همهٔ مخزن‌های قبلی شکستند. | نردبان مدل (۵.۸) + ورک‌فلوی سلامت هفتگی که مدل پیش‌فرض را با یک درخواست کوچک تست می‌کند و اگر مرد، ایشو باز می‌کند. |
| **دو نسخه از فایل‌های ایجنت** | `app/src/main/assets/` و `docs/github/` باید بایت‌به‌بایت یکی بمانند و هیچ‌چیز این را اجبار نمی‌کند. | یک قدم در CI: `diff -r` بین دو پوشه؛ ناهماهنگی = build قرمز. |
| **`web/` عقب‌افتاده** | پرامپت `web/server/src/prompt.ts` هنوز اسکیمای چهارکلیدی قدیمی را دارد (بدون `task_description`) و از اپ جدا افتاده. | یا هم‌ترازش کنید یا تا زمان کار جدی روی وب، صریحاً «آزمایشی» علامتش بزنید. |
| **سریال‌سازی سراسری** | `concurrency.group: agent-worker` یعنی روی هر مخزن فقط یک ایجنت همزمان. با تجزیه به چند ایشو، این گلوگاه می‌شود. | گروه را به‌ازای ایشو کنید و فقط مرحلهٔ merge را سریال نگه دارید. |
